## Архитектурные правила (НЕ нарушать)

1. **Вся бизнес-логика — в `server/`**, НЕ в React-компонентах. Компонент отображает и зовёт server-функцию. Логика расчётов, валидаций, движений склада — только в server-слое.
2. **Балансы и стоимость — вычисляются, НЕ хранятся.** Баланс тары = Σ движений. Стоимость = принятый вес × цена строки контракта (живой пересчёт). Никаких закешированных сумм в таблицах.
3. **Единый складской движок.** Тара и ингредиенты — одна сущность StockMovement с дискриминатором `kind`. Не создавай отдельные таблицы движений.
4. **Soft delete** для справочников (active=false), никогда не физическое удаление сущностей со связями.
5. **RBAC на сервере И клиенте.** Скрыть кнопку на фронте недостаточно — server-функция обязана проверять роль (`requireRole`).
6. **ChangeLog** на все правки цены, привязки контракта, статусов, актов приёмки. Запись — через `logChange()` в ТОЙ ЖЕ транзакции, что и изменение. Проверять результат строками в БД, не только отсутствием ошибки.
7. **Идемпотентность плеч склада — НЕТТО, не по существованию.** Откаты — нетто-сторно (append, не delete), поэтому оригиналы движений остаются в леджере. Гард «if (existing) skip» блокирует легитимное повторное применение после полного цикла (баг materials-fix). Любое НОВОЕ плечо: гард по нетто группы (применять, если нетто=0; пропускать, если уже активно).

## Четыре базы веса (критично, частый источник ошибок)

- **Тара** двигается по **плановому** весу при переходе `planned → sent` (не при создании, не пересчитывается на приёмке).
- **Ингредиенты** расходуются по **фактическому** весу (перевеска).
- **Выполнение контракта (тонны)** считается от **принятого** веса (после брака).
- **Стоимость (деньги)** считается от **оплачиваемого** веса = принятый + корректировка расчёта (BR-33). Без корректировки равен принятому. ⚠ Раньше правило звучало «деньги = принятый вес» — устарело: принятый ≠ оплачиваемый.
- **Брак** — статистика, база — фактический вес, в выполнение НЕ идёт.

Подробности и все формулы — в DOMAIN.md разделы 1, 4, 5.

## Эталонные паттерны (выработаны на этапе A — копировать, не изобретать)

- **CRUD-модуль:** `server/<entity>/{schema.ts,actions.ts}` + страницы в `app/(app)/...`. Эталон — Farmer (`server/farmers/`).
- **schema.ts** — единая zod-схема (источник типов формы и серверной валидации). Условная валидация — через `superRefine`.
- **actions.ts** — Server Actions, возвращают `ActionResult` (единый формат успех/ошибка). Внутри: `requireRole` → zod-валидация → `$transaction` (запись + `logChange`).
- **Soft delete:** одна server-action `set<Entity>Active(id, active)` туда-обратно, в UI — кнопка по статусу строки (деактивация с AlertDialog).
- **Клиентский RBAC:** `components/auth/RoleGate.tsx`. Серверный: `server/auth/session.ts` → `requireRole`.
- **Валидаторы:** общие в `lib/validators.ts` (`phoneSchema`, `normalizePhone`, `formatPhone` «+7 XXX XXX-XX-XX»). Телефоны в UI — кликабельные `tel:`.
- **FK-Select в формах:** связанная сущность не теряется при редактировании — **фактически привязанное значение ВСЕГДА присутствует в опциях** (неактивное · из другого сезона · вне текущей выборки), помечается. Иначе селект с валидным `value` рисует плейсхолдер и показывает «не привязано» при живой привязке (реальный дефект acceptance-ux-1: строка контракта из другого сезона отсутствовала в `contractLines`).
- **«Сегодня» — только через `todayLocalISO()`** (`server/shipments/workdays.ts`, зона `FACTORY_TZ = "Europe/Moscow"`), НЕ `new Date().toISOString()`: UTC-«сегодня» до 03:00 по местному времени отдаёт вчерашнюю дату. Хранение дат в БД остаётся UTC-полуночью (`parseDateUTC` не трогать) — меняется только вычисление «какое сегодня число». Клиентские места тоже обязаны использовать хелпер, иначе браузер и сервер разойдутся. **То же правило — для ГРАНИЦ периодов** (фильтры «с/по», отчёты): границы считаются в `FACTORY_TZ`, а не UTC-полуночью, иначе правка в 00:30 МСК выпадает из фильтра своего дня (закрыто в changelog-viewer).
- **Decimal** в Prisma для всех весов/цен/количеств.

## Конвенции кода

- Структура: `app/` (страницы), `server/` (логика, по доменам: shipments/inventory/contracts/acceptance/analytics), `prisma/schema.prisma`, `components/ui/` (shadcn).
- TypeScript строгий. Типы из Prisma переиспользовать, не дублировать вручную.
- Server Actions предпочтительнее ручных REST-эндпойнтов.
- Названия сущностей в коде — как в DOMAIN.md (Shipment, ShipmentItem, StockMovement…).
- Не использовать localStorage/sessionStorage — состояние в React state или БД.
- **Verify-скрипты (`scripts/*-verify.ts`) и их стабы (`scripts/_stubs/`) — часть репозитория, НЕ gitignore.** Стабы (`@/auth`, `next/cache`) подменяются per-script через Node `registerHooks` (resolve-хук) — это осознанно opt-in. **Никогда** не заводить стабы глобальным алиасом в `tsconfig`/`next.config`: `_stubs/auth.ts` заставляет `requireRole` пропускать любого пользователя, и попадание такого алиаса в сборку = дыра в RBAC. Импортов из `app/`/`server/` в `_stubs` быть не должно.
- **Юнит-тесты (audit-w3):** vitest, файлы `<модуль>.test.ts` **рядом с исходником** (co-located), запуск `npm run test` (watch — `npm run test:watch`). Покрываем ЧИСТЫЕ функции ядра расчётов; `describe/it/expect` импортировать явно из `"vitest"` (без `globals`, иначе `tsc`/`next build` потребуют доп. типов). Тесты фиксируют **инварианты** (четыре базы веса, UTC-дисциплина дат, ceil тары, точность Decimal), а не процент покрытия. Расхождение теста с реализацией — повод для разбора, а не для правки теста «под код». Всё, что ходит в БД, остаётся за verify-скриптами.
- **CI (`.github/workflows/ci.yml`):** `lint` + `typecheck` + `test` на push/PR в `dev` и `main`. **`npm run build` в CI не запускать** — в нём `prisma migrate deploy`, который полез бы в реальную БД; вместо этого отдельный шаг `npx prisma generate` (без него `tsc` падает на импортах Prisma-типов) с фиктивным `DIRECT_URL`: `prisma.config.ts` зовёт `env("DIRECT_URL")` при загрузке, а конфиг грузит любая команда CLI.

## Данные: dev vs прод (правило проекта)

**Прод запущен** (Vercel + отдельная прод-ветка Neon, см. `docs/prompts/PROD-DEPLOY.md`). Действует разделение:

- **Dev-ветка Neon (разработка/preview) — тестовая, данные одноразовые** (нет ценности). Миграции и рефакторинги могут свободно удалять/пересоздавать данные; data-preserving миграции на dev НЕ требуются. Для проверок допустимы rolled-back транзакции или прямое удаление тест-данных.
- **Прод-БД — ЦЕННЫЕ реальные данные.** Никогда не вайпать. **Прод-миграции обязаны быть data-preserving**; деструктив (drop/rename колонки, смена типа) — только осознанно, с бэкапом (`pg_dump`) и ревью. Прод-миграции применяются `prisma migrate deploy` (НЕ `migrate dev`) на build Vercel из ветки `main`.
- Правило dev-вайпа к проду **НЕ применять**. Если задача касается прод-данных/прод-миграции — сверяться с `PROD-DEPLOY.md` и при сомнении спрашивать.

## Принцип работы

- Делаем **вертикальными срезами**: один модуль доводится до рабочего состояния перед следующим. Не распыляться.
- Не over-engineering: без Docker, Redis, микросервисов, GraphQL, очередей. Монолит Next.js, агрегаты на лету.
- Объясняй неочевидные решения коротко — разработчик junior-уровня, код должен быть понятен и сопровождаем.
- После завершённой задачи — обновить статус в TASKS.md и предложить коммит.
- **Планирование — одно-фермерскими плановыми `Shipment`; машины собираются merge'ем** (переназначение `shipment_id` позиций; разборка — по `farmer_id`). Плановые НЕ имеют StockMovement → merge/disassemble не трогают склад; только над planned.
- **Правка отгрузки — только в статусе `planned`** (через цепочку откатов accepted→arrived→sent→planned). Прямая правка sent/arrived запрещена (тара двинута по плановому весу → десинхрон плеч).
- **Неделя/вид планировщика и ленты — в URL** (`?week=YYYY-Www` дефолт текущая, `?view=`). Без localStorage.

## Чего НЕ делать без спроса

- Не менять схему данных (она заморожена) — при необходимости миграции сначала обсудить. **Утверждённая миграция B4** (обсуждена, см. DOMAIN BR-20/21/22): `WeeklyPlan` += `season_year`, `date Date?` (nullable; null=недельная цель) + partial-unique индексы; убедиться, что `ShipmentItem.actual_weight_kg` присутствует в схеме (уже в DOMAIN — добавить колонку, если миграции ещё не было). **Состав недели (B4c, обсуждён, BR-23):** новая таблица `WeeklyPlanScope` (season_year, iso_year, iso_week, culture_id; уникум по неделе+культуре). **Применённая миграция C2 (`c2_ingredient_consumption`, обсуждена):** `MovementType += consumption` (расход ингредиента в производство, `from=фермер · to=null`), `SourceDocType += acceptance_act` (привязка движений к акту), `StockMovement.quantity` расширена `Decimal(12,3) → Decimal(15,6)` (микродозы ингредиентов, напр. аскорбинка ~0,00005). Иные изменения схемы — по-прежнему через обсуждение.
**Этап E (ингредиенты, E1–E4) — БЕЗ миграции** (подтверждено): схема уже полиморфна (`MaterialShipmentItem.item_kind`+`ingredient_id`, `StockMovement.kind=ingredient`, `MovementType.delivery/opening`, `SourceDocType.material_shipment`). Доставка ингредиента — тот же `MaterialShipment`, параметризованный по `item_kind` (вариант A: единый движок, не ingredient-копии); смешанный груз (тара+ингредиент в одном рейсе) — штатный кейс; транзит ингредиента только `-2`.
**transfer (farmer→farmer):** `MaterialShipment += source_farmer_id Int?` (null=доставка с завода, заполнено=перенос от фермера) + транзит-сентинел `-3`. Движок доставки обобщён по origin+transit (вариант A, не зеркалить). **D3-2:** `MaterialShipmentItem += arrived_at` (позиционное прибытие). Прочие изменения схемы — через обсуждение.
- Не добавлять зависимости вне утверждённого стека без обоснования.
- Не реализовывать фичи вне текущего этапа TASKS.md (не забегать вперёд по роадмапу).
- Не вставлять код, назначение которого не объяснено.
