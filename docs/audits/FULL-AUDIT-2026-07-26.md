# Полный аудит проекта VSMS — 26.07.2026

Аудит выполнен по коду репозитория (app/, server/, prisma/, lib/, docs/) + `npm audit`.
Что НЕ проверялось (нет доступа/данных): рантайм на проде, реальные объёмы данных в Neon, настройки Vercel/Neon (env, бэкапы), фактические планы запросов Postgres. Выводы по производительности на реальных данных — расчётные.

Формат: каждая находка — серьезность (Critical/High/Medium/Low) + уверенность (Высокая/Средняя/Низкая).

## Этап 1. Обзор проекта

**Назначение:** внутренняя система управления поставками овощного сырья на консервный завод (замена Excel/Google Sheets). Solo-разработка, реальный рабочий инструмент, прод запущен.

**Архитектура:** монолит Next.js (App Router) с чётким разделением: `app/` — страницы и клиентские компоненты, `server/` — вся бизнес-логика по доменам (shipments, acceptance, inventory, contracts, materials, plan, analytics...), `prisma/` — схема и миграции, `lib/` — утилиты. Мутации — через Server Actions с единым `ActionResult`. Склад — единый append-only леджер `StockMovement`, балансы вычисляются суммой движений.

**Стек:** Next.js 16.2.7, React 19, TypeScript strict, Prisma 7 + Neon (pooled/direct), Auth.js v5 (Credentials + JWT), Tailwind 4 + shadcn/ui, @dnd-kit, Recharts, SheetJS.

**Организация:** предметно-ориентированная, каждый домен — `schema.ts` (zod) + `actions.ts` + чистые хелперы. Эталонные паттерны реально соблюдаются во всех модулях. Документация (`docs/DOMAIN.md`, PRD, DESIGN, TASKS) — выдающаяся для solo-проекта: бизнес-правила пронумерованы (BR-1…BR-25), код на них ссылается.

**Поддерживаемость:** высокая по структуре и комментариям; риски — отсутствие автотестов и рост пары монстр-компонентов (см. Этап 3).

**Сильные стороны архитектуры:** леджер вместо хранимых балансов (аудируемость, откаты нетто-сторно), полиморфный движок тара/ингредиенты без дублирования таблиц, RBAC на сервере, вычисляемая стоимость (нет рассинхрона кешей), дисциплина UTC-дат.

## Этап 2. Сильные стороны

1. **Доменная документация как источник истины** (`docs/DOMAIN.md` + BR-нумерация, сквозные ссылки из кода: «BR-7», «BR-19» в сообщениях об ошибках). Резко снижает стоимость сопровождения и передачи контекста. Уверенность: Высокая.
2. **Append-only складской леджер с нетто-сторно** (`server/shipments/actions.ts: revertShipmentToPlanned/ToSent`, `server/acceptance/act.ts: revertActItemWithin`, `server/shipments/packaging.ts: applyInboundArrivedTareLeg`). Откаты не удаляют историю, идемпотентность по нетто группы — грамотное решение, редко встречающееся даже в командной разработке.
3. **Единообразие CRUD-модулей**: zod-схема = источник типов формы и серверной валидации, `requireRole → validate → $transaction (+logChange)` везде. Копипаст паттерна вместо изобретения — правильная стратегия для solo+AI.
4. **Серверный RBAC во всех мутациях** (`requireRole("admin")` / `("operator","admin")`), клиентский `RoleGate` — только UX. Проверено по всем `actions.ts`.
5. **ChangeLog в той же транзакции, что и изменение** (`server/changelog.ts` + все actions) — аудит не может разъехаться с данными.
6. **Decimal для всех весов/цен** (Prisma.Decimal, `Decimal(15,6)` для микродоз ингредиентов) — нет накопления float-ошибок в деньгах и тоннах.
7. **Дисциплина таймзон**: все даты парсятся `parseDateUTC`, день недели не плывёт (`server/shipments/workdays.ts`) — частая ошибка в подобных системах здесь системно закрыта.
8. **Пакетная загрузка вместо N+1** (`loadPackagingContext`, includes в `feed-loader.ts`) — осознанная работа с запросами.
9. **Разделение dev/prod данных и миграций** (CLAUDE.md, `prisma.config.ts` с direct/pooled) — прод-данные защищены процессом.
10. **Комментарии объясняют «почему», а не «что»**, включая исторические баги (гард «if existing» из materials-fix). Это лучший тип комментариев.

## Этап 3. Проблемы

### Безопасность / зависимости

**П-1. Уязвимые версии next-auth/@auth/core.** Critical · Уверенность: Высокая.
- Где: `package.json` → `next-auth 5.0.0-beta.31` (тянет @auth/core ≤0.41.2). `npm audit`: 3 advisory, включая критический (GHSA-xmf8-cvqr-rfgj — необработанное исключение на malformed Bearer header).
- Последствия: DoS/обход отдельных механизмов auth-слоя, на котором держится весь доступ.
- Сложность исправления: низкая — `npm audit fix` / обновить next-auth beta.
- Рекомендация: обновить немедленно, прогнать логин/сессию/роли вручную.

**П-2. Уязвимая версия Next.js 16.2.7.** High · Уверенность: Высокая.
- Где: `package.json`. `npm audit`: серия advisory, среди них «Middleware/Proxy bypass в App Router» и «Unauthenticated disclosure of internal Server Function endpoints».
- Почему критично именно здесь: вся авторизация зоны (app) висит на `proxy.ts` (middleware) — advisory бьют ровно в эту модель.
- Исправление: обновить Next до патч-версии из advisory. Низкая сложность, но обязательный smoke-тест прод-сценариев.

**П-3. `xlsx 0.18.5` — Prototype Pollution + ReDoS, фикса на npm нет.** Medium · Уверенность: Высокая (наличие CVE), Средняя (эксплуатируемость).
- Где: `lib/xlsx-export.ts` — единственная точка. Только запись (экспорт), чужие файлы не парсятся → реальная поверхность атаки мала. npm-пакет SheetJS заброшен.
- Рекомендация: перейти на официальный дистрибутив SheetJS (cdn.sheetjs.com) или `exceljs`. Не срочно, но зафиксировать как долг.

**П-4. Роль и активность пользователя вморожены в JWT на весь срок жизни сессии.** High · Уверенность: Высокая.
- Где: `auth.config.ts` — `strategy: "jwt"`, роль кладётся в токен при логине; `authorize` проверяет `user.active` только при входе. maxAge не задан → дефолт Auth.js 30 дней.
- Последствия: уволенный/деактивированный сотрудник или пониженный в роли пользователь сохраняет доступ до 30 дней. Для системы с реальными прод-данными это дыра процесса offboarding.
- Исправление: в `jwt`-callback периодически (например, раз в N минут по `token.iat`) перечитывать пользователя из БД (active + role) и обнулять токен при несоответствии; и/или сократить `session.maxAge`. Сложность: низкая.

**П-5. Read-функции в "use server"-файлах без auth-гарда.** Medium · Уверенность: Средняя.
- Где: `server/shipments/actions.ts` → `getShipments`, `getShipment`, `getTripWeightNorm`, `listShipmentOptions` — нет `requireRole()`. Аналогично `server/acceptance/board.ts` (но он без "use server" — ок, server-only).
- Почему проблема: экспорт из "use server"-модуля — это публичный HTTP-эндпойнт. Защита опирается только на middleware-matcher `proxy.ts`, который исключает `/login` и `.*\..*` — в связке с П-2 (обход middleware) данные читаются без аутентификации. Уверенность средняя: эксплуатация зависит от версии Next, но принцип defense-in-depth нарушен, тогда как в `inventory/balances.ts` гард `await requireRole()` стоит.
- Исправление: добавить `await requireRole()` во все читающие экспортируемые server actions. Сложность: минимальная.

**П-6. Нет rate limiting / защиты от перебора пароля.** Medium · Уверенность: Высокая.
- Где: `auth.ts` authorize, `app/login/actions.ts`. Ни задержек, ни лимитов, ни lockout.
- Последствия: перебор паролей по известному логину. Смягчение: bcrypt(10) замедляет, юзеров мало.
- Исправление: простейший in-memory/DB счётчик неудач с задержкой, или Vercel WAF-правило. Сложность: низкая.

**П-7. Нет security-заголовков.** Low · Уверенность: Высокая.
- Где: `next.config.ts` пуст. Нет CSP, HSTS, X-Frame-Options и т.д.
- Исправление: блок `headers()` в next.config. Для внутреннего инструмента приоритет низкий.

### Корректность / возможные баги

**П-8. Гонка генерации `Shipment.code` + отсутствие unique.** Medium · Уверенность: Высокая (по коду), Низкая (по вероятности срабатывания).
- Где: `server/shipments/actions.ts: getNextCode` — `MAX(code::int)+1` внутри транзакции; `prisma/schema.prisma` — `Shipment.code String` **без `@unique`**.
- Почему: два параллельных создания при read committed прочитают одинаковый MAX → дубль кода машины. БД не защитит — констрейнта нет. При одном admin-пользователе вероятность мала, но код машины — рабочий идентификатор для людей.
- Исправление: `@unique` на `code` (+ retry при P2002) или Postgres sequence. Сложность: низкая (миграция обсуждаемая — схема заморожена).

**П-9. Гонка авто-перехода машины в accepted.** Medium · Уверенность: Средняя.
- Где: `server/acceptance/act.ts: saveAct` — `stillUnaccepted === 0` считается count'ом внутри транзакции.
- Почему: две параллельные приёмки последних двух позиций могут обе увидеть «ещё есть непринятые» → машина навсегда остаётся arrived при полностью принятых позициях. UI это покажет некорректно; чинится только повторным пересохранением акта.
- Последствия: редкий, но запутывающий рассинхрон статуса. Смягчение: приёмкой занимается 1–2 человека.
- Исправление: пересчитывать статус машины отдельным идемпотентным шагом (recompute по факту) или `SELECT ... FOR UPDATE` на shipment. Сложность: средняя.

**П-10. Проверка «прошедший день» в UTC, а не в локальном времени.** Low · Уверенность: Высокая.
- Где: `server/shipments/actions.ts: createWholeMachines` — `const today = new Date().toISOString().slice(0,10)`.
- Почему: для UTC+3 с 00:00 до 03:00 «сегодня» по серверу — ещё вчера: система разрешит создать план на прошедший локальный день (и наоборот около полуночи). Тот же паттерн вероятен в других местах со «сегодня».
- Исправление: единый хелпер `todayLocalISO(tz)` с фиксированной заводской таймзоной. Сложность: низкая.

**П-11. Гард расхода ингредиентов — по существованию, не по нетто.** Low · Уверенность: Высокая.
- Где: `server/acceptance/act.ts: saveAct` — `already === 0` (count движений по акту).
- Почему: нарушает собственное правило проекта (CLAUDE.md, правило 7: «любое НОВОЕ плечо — гард по нетто»). Сейчас спасает то, что откат удаляет акт и новый акт получает новый id (source_doc_id меняется). Если когда-нибудь откат перестанет удалять акт или появится пересчёт расхода при изменении веса — молча пропустит повторное применение (точный сценарий бага materials-fix).
- Исправление: заменить count на нетто-гард, как в остальных плечах. Сложность: низкая.

**П-12. Ошибки в catch проглатываются без логирования.** Medium · Уверенность: Высокая.
- Где: все `actions.ts` — `catch (e) { return authFail(e) ?? { ok:false, error:"Не удалось..." } }`. `console.error(e)` нет нигде.
- Последствия: на проде реальная причина сбоя (сломанная миграция, constraint, таймаут Neon) невидима — пользователь видит «Не удалось сохранить», разработчик не видит ничего. Диагностика инцидентов по прод-данным станет мучительной.
- Исправление: один хелпер `failWithLog(e, msg)` с `console.error` (Vercel собирает логи) — правка на полчаса. Дальше — Sentry (см. роадмап).

### Производительность / масштабируемость

**П-13. Балансы = полное сканирование леджера на каждый показ.** Medium сейчас → High через 2–3 сезона · Уверенность: Высокая.
- Где: `server/inventory/balances.ts: getTareBalances` (и аналог для ингредиентов) — `findMany` ВСЕХ StockMovement kind=packaging + агрегация в JS. Леджер append-only и не сворачивается никогда (сторно только добавляют строки).
- Последствия: линейная деградация каждого экрана балансов И каждого перехода по (app) — `getActiveAlerts` в `app/(app)/layout.tsx` дёргает те же полные агрегации на каждую навигацию (в коде это честно признано).
- Исправление: (а) SQL-агрегация `GROUP BY` вместо переноса строк в JS — час работы, снимет 80% боли; (б) позже — годовой opening-снэпшот с закрытием сезона. Сложность: низкая/средняя.

**П-14. Нет индексов под реальные паттерны запросов.** Medium · Уверенность: Высокая.
- Где: `prisma/schema.prisma`. Отсутствуют: `Shipment @@index([arrival_date])` (все выборки ленты/доски фильтруют по arrival_date), `StockMovement @@index([source_doc_type, source_doc_id])` (все откаты и гарды читают по документу), индекс на `ShipmentItem.shipment_id` и `ChangeLog @@index([entity, entity_id])`. Postgres не индексирует FK автоматически.
- Последствия: seq scan на растущих таблицах; откаты и лента замедлятся первыми.
- Исправление: одна data-preserving миграция с 4 индексами. Сложность: низкая.

**П-15. `getFeed` грузит весь сезон с глубокими include.** Low сейчас · Уверенность: Высокая.
- Где: `server/shipments/feed-loader.ts` — все Shipment сезона + items + акты + калибры + водители.
- При сотнях машин за сезон терпимо; к концу второго сезона страница потяжелеет. `loadWeekShipments` уже умеет грузить по неделе — лента может перейти на диапазон недель. Сложность: средняя.

### Качество кода / поддерживаемость

**П-16. Монстр-компоненты на клиенте.** Medium · Уверенность: Высокая.
- Где: `app/(app)/planner/_components/BoardView.tsx` — 932 строки; `ShipmentsFeed.tsx` — 859; `TareBalanceMatrix.tsx` — 816; `AcceptanceActDialog.tsx` — 743.
- Почему: сервер-слой дисциплинирован, а клиент — нет: state, dnd, диалоги, форматирование в одном файле. Это главные будущие точки боли при правках UI (и худшее место для AI-правок — большой контекст, легко сломать соседнее).
- Исправление: выносить хуки (`useBoardDnd`, `useFeedFilters`) и презентационные подкомпоненты при каждой следующей правке этих файлов (правило бойскаута), не отдельным рефакторинг-марафоном.

**П-17. Дублирование mobile/desktop-компонентов.** Low · Уверенность: Средняя.
- Где: пары `AcceptanceActDialog`/`MobileActDialog`, `ShipmentsFeed`/`MobileShipmentsFeed` и др.
- Валидация и расчёты живут на сервере (хорошо), но UI-логика (сборка формы акта) частично задвоена — правки нужно вносить дважды. Осознанный trade-off, но фиксирую: при расхождении поведения mobile/desktop искать здесь.

**П-18. Мёртвый код: `getShipments`.** Low · Уверенность: Высокая.
- Где: `server/shipments/actions.ts: getShipments` — не используется нигде в app/ (лента ходит через feed-loader). При этом это unguarded endpoint, отдающий ВСЕ отгрузки (см. П-5).
- Исправление: удалить.

**П-19. README — дефолтный boilerplate create-next-app.** Low · Уверенность: Высокая.
- Реальная документация в docs/ отличная, но входная точка репозитория врёт о проекте. 15 минут: назначение, ссылки на docs/, setup (две строки Neon, seed).

**П-20. `logChange` не проверяет результат записи.** Low · Уверенность: Высокая.
- Где: `server/changelog.ts` — `createMany` без сверки count, хотя CLAUDE.md требует «проверять результат строками в БД». Внутри транзакции ошибка её откатит, так что риск мал; но молчаливый `if (list.length === 0) return` маскирует забытый пустой диф.

### Тестирование / CI

**П-21. Ноль автоматических тестов, ноль CI.** High · Уверенность: Высокая.
- Где: нет `*.test.ts`, нет `.github/`. Есть 10 ручных verify-скриптов (`scripts/*-verify.ts`) — это хорошо, но они не запускаются автоматически и требуют живой БД.
- Почему это главная системная проблема: ядро системы — инварианты леджера (нетто-идемпотентность, три базы веса, цепочки откатов). Именно их проще всего сломать будущей правкой, и именно они дешевле всего покрываются юнит-тестами чистых функций (`calcPackagingUnits`, `workdays.ts`, netto-агрегации, `calcIngredientConsumption` — всё уже чистое, тестируется без БД!).
- Последствия: каждый рефакторинг на прод-данных — русская рулетка; регресс заметит пользователь на реальных поставках.
- Исправление: vitest + 20–30 юнит-тестов чистых функций (1–2 дня), GitHub Actions `lint + tsc + test` на PR (полдня). Verify-скрипты постепенно конвертировать в интеграционные тесты против dev-ветки Neon.

## Этап 4. Потенциальные ошибки (сводка подозрительных мест)

Уже описаны как проблемы: П-8 (дубль code), П-9 (гонка accepted), П-10 (UTC-«сегодня»), П-11 (гард по существованию).

Дополнительно, с пометкой «не уверен»:

- **`seasonYearOf` по дате прибытия vs отправления** (`acceptance/act.ts: getActContext` — `arrival ?? departure ?? now`): машина, едущая через границу сезона (31 мая → 1 июня), получит строки контрактов нового сезона, а её план учтён в старом. Крайне редкий кейс (июнь — не сезон границы поставок?). Уверенность: Низкая — возможно, доменно невозможно.
- **`withinSummerRange` сравнивает (месяц, день) без года** (`workdays.ts`): корректно, пока лето не пересекает границу года — комментарий это фиксирует; если завод когда-то сместит «лето» на октябрь–март, тихо сломается. Уверенность: Высокая в текущей безопасности, риск только при изменении домена.
- **`assembleShipments`: `target = ids[0]`** — целевая машина определяется порядком массива с клиента; при случайной перестановке коды машин «переедут». Не баг, но хрупкий контракт API. Уверенность: Средняя.
- **`persistShipmentItems` — delete+recreate позиций** меняет `ShipmentItem.id` при каждой правке плановой отгрузки. Сейчас безопасно (у planned нет актов и движений), но любой будущий FK на позицию (фото, комментарии) молча осиротеет. Уверенность: Высокая.

## Этап 5. Безопасность (сводный аудит)

## Этап 11. Итоговое заключение (Tech Lead)

**Главные достоинства.** Это не «учебный проект с AI», а зрелая доменная система: append-only леджер с нетто-идемпотентными откатами, дисциплина Decimal/UTC, серверный RBAC, транзакционный аудит и документация уровня, который редко встречается в командах из десяти человек. Паттерны не декларированы, а реально соблюдаются во всех 20+ модулях.

**Главные недостатки.** Контур безопасности отстал от кода: уязвимые версии именно auth-стека и фреймворка, замороженная в JWT роль, незащищённые чтения. Второе — ноль автотестов при леджере, чья корректность держится на инвариантах, которые проще всего сломать молча. Третье — прод-ошибки никуда не логируются.

**Самые рискованные места.** (1) Цепочки откатов статусов и плечи склада — любая будущая правка без тестов; (2) middleware-центричная авторизация на уязвимой версии Next; (3) экраны балансов/алертов как первая точка деградации производительности.

**Обязательно исправить (прод уже живой — «перед релизом» = сейчас):** П-1, П-2 (обновления), П-4 (JWT), П-5 (гарды чтений), П-12 (логирование). Всё вместе — 1–2 дня.

**Можно оставить как есть:** архитектуру целиком, схему БД (кроме индексов/unique), паттерн delete+recreate позиций, дубли mobile/desktop, отсутствие кэша и pagination, монолит без Docker — всё адекватно масштабу.

**Зрелость проекта:** 7/10 — выше среднего прод-уровня по архитектуре и документации, ниже — по операционке (тесты, мониторинг, зависимости).

**Готовность к развитию:** высокая. Эталонные паттерны + DOMAIN.md означают, что новые модули добавляются предсказуемо. Единственный реальный тормоз развития — отсутствие тестовой сетки под ногами.
