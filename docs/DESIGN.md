# DESIGN.md — UX-решения по экранам

Источник истины по структуре экранов. Визуальные токены — в `DESIGN-SYSTEM.md`
(подчиняется правилам раздела «Дизайн» в CLAUDE.md). Утверждено по итогам
этапа B0 (прототип: `docs/prototypes/lenta-b0.html`).

---

## 1. Каркас приложения

- Левый сайдбар: логотип VSMS; навигация — Лента отгрузок, Планировщик,
  Приёмка, Контракты, Тара, Ингредиенты, Логистика материалов, Аналитика,
  Справочники, Настройки. Активный пункт — заливка `canvas-soft-2`.
- Контент: заголовок страницы + подзаголовок-контекст
  («Овощное сырьё на завод · сезон 2026»).
- Контейнер контента: fluid, ширина 100% минус паддинги 24–32px,
  max-width 1880px, центрирование на более широких экранах.

## 2. Лента отгрузок (главный экран)

### Тулбар
- «+ Отгрузка» (primary, чёрная) → диалог «Отгрузка» (раздел 4).
- Переключатель недели ‹ Неделя N даты › + кнопка «Сегодня».
- Поиск: фермер, культура, № акта.
- Фильтры: Поставщик, Сырьё, Статус (combobox с поиском).
- Тумблер «Скрыть плановые». Экспорт Excel.
- Переключатель видов: Таблица | Heatmap | План (B3 — только Таблица,
  остальные — заглушки/скрыты до своих этапов).

### Группировка
- Недели ISO (BR-17). Шапка недели: чип `W{N}` (mono) + «Неделя N ·
  даты · год (Пн–Сб|Пн–Пт по сезону)» + чипы культур с недельными
  суммами (т) + справа «N машин · X т». Прошлые недели свёрнуты
  (разворачиваются кликом), текущая и будущие развёрнуты.
  При входе — скролл к текущей неделе.
- Дни (по дате ПРИБЫТИЯ): шапка «День недели, дата» + чипы культур
  дня + справа «тара: N ящиков · M бочек». Пустой день — одна строка
  «— нет отгрузок».

### Машина (двухзонный леджер)
Article-блок, машина = блок строк. Код машины НЕ показывается
(опознание: водитель/груз/даты).

**Левая зона** (фон = цвет статуса, фикс. ширина — вмещает
«30 сентября → 2 октября» с зазором до карандаша ≥8px):
- Строка 1: бейдж статуса · даты «{отправление} → {прибытие}»
  (полные месяцы, акцент weight 600 на прибытии, tabular-nums) ·
  карандаш у правого края (один на машину → диалог «Отгрузка»).
- Строка 2: «Фамилия И. О. · ТК» кликабельно → модалка водителя;
  без водителя — «водитель не назначен» приглушённо.
- Комментарий (если есть): нижней строкой под пунктирным разделителем.

**Правая зона** — строка на позицию (1–4), строки делят высоту машины
поровну (flex 1, контент по вертикальному центру), подложка = Culture.color
8–10% opacity на всю высоту строки. Без шапки колонок, без карандашей
на строках. Колонки:
- чип-квадрат цвета культуры + название;
- вес: tabular-nums + «кг» приглушённо;
- фермер;
- тара: «{тип} · {N} шт» — информационно, расчёт ceil по нормам
  (DOMAIN раздел 3); культура без тары — пусто;
- статус приёмки позиции (последняя колонка, **по ПОЗИЦИИ независимо от машины**,
  BR-13). Состояния: не отправлена → «— не отправлена»; отправлена без веса →
  «— приёмка»; есть перевеска, не принята → «факт {вес} кг»; принята актом →
  «факт {вес} кг · к оплате {принятый} кг». «К оплате» = accepted_weight (simple:
  факт×(1−брак%); calibre: Σ принятых категорий). Принятая позиция может стоять
  в машине, которая ещё «Прибыла»/«Частично принята». Числа в ленте округляются
  до целых (информативная зона; точные — в статистике/аналитике). Бейдж «принят»
  на позиции — отдельно от производного статуса машины.

**Цвета статусов** (две заливки — `zone` левой зоны / `badge` бейджа,
канон в `DESIGN-SYSTEM.md` → `status-fills`): planned `zone #f5f5f5 /
badge #ededed` · sent `zone #eaf2ff / badge #d3e5ff` · arrived
`zone #fff6e3 / badge #ffefcf` · accepted `zone #ddfff7 / badge #c7f6ea`.
Точка/текст бейджа: planned #b3b3b3/#888888 · sent #0070f3/#0761d1 ·
arrived #f5a623/#ab570a · accepted #29bc9b/#1d8e75. (Не `#aaffec`.)

### Модалка водителя
ФИО (заголовок), бейдж ТК, телефон — `tel:`-ссылка, инфо-блок (машина,
свободный текст), кнопки «Скопировать телефон» / «Скопировать всё»
(не переполняют футер).

## 3. Действия со статусами (из B2, диалоги утверждены)
- planned: «Отправить» (admin) → confirm-диалог с предпросмотром списания
  тары. **Предпросмотр группируется ПО ФЕРМЕРУ** (не по позиции), строки
  по типам тары, итог снизу («Итого: 62 ящика · 9 бочек»). **Случай «нет
  нормы» — частичный:** рассчитанные позиции показываются как «будет
  списано», ОТДЕЛЬНЫЙ красный (error) блок «не рассчитана тара — нет нормы»
  со списком троек фермер×культура×тип; кнопка «Отправить» disabled, пока
  есть хоть одна нерассчитанная позиция; «Отмена» активна. Подсказка ведёт
  в Настройки → Нормы.
- sent: «Откатить в план» (admin) → confirm с предпросмотром возврата тары
  по фермеру + текст про сторно и журнал. Кнопка «Откатить» — обычная
  primary (обратимое штатное действие), НЕ деструктивно-красная.
- Правка/удаление — только planned. Карандаш у sent+: для admin
  открывает диалог с заблокированными полями и подсказкой «для правки
  откатите статус», для остальных скрыт.
- Прототип диалогов: `docs/prototypes/status-dialogs-*.html`.

## 4. Диалог «Отгрузка» (создание = редактирование, одна форма)
- Заголовок «Отгрузка» (+ статус-бейдж при редактировании).
- Даты: «Отправление» и «Прибытие» рядом; хинт: «введите одну дату —
  вторая подставится (±2 дня), обе можно править». Валидация BR-11/BR-12
  серверная, ошибки под полями.
- Водитель: combobox с поиском по фамилии, опции «Фамилия И. О. · ТК»,
  необязателен (обязателен при отправке — проверка перехода).
- Комментарий: textarea 2 строки.
- Позиции (1–4), каждая — фермер (select) · культура (select) · вес кг ·
  **тип тары** (зависит от культуры: 0 типов = навал, поля нет; 1 тип =
  select скрыт, тип авто + приглушённая метка; ≥2 типов = select с
  предвыбранным is_default, сменяемый) · строка контракта (select «label ·
  цена ₽/кг»; опции = строки контрактов фермера+культуры сезона; ровно одна
  → автоподстановка, редактируема) · тара — информационная строка «Тара:
  ≈ N {ед}» / «нет нормы», НЕ поле ввода · крестик удаления.
  Все зависимые поля пересчитываются при смене культуры/фермера (единый
  каскадный хук, 17a). «+ позиция» (disabled при 4). Дубль фермер+культура
  разрешён (разные типы тары — разные позиции).
- Футер: Отмена / Сохранить (primary).

## 5. Настройки → Нормы (3 режима)
Сегментированный переключатель на 3 положения под подтабами Настроек:
- **Нормы тары** — матрица фермер × культура, ячейка = нетто-норма (кг на
  единицу тары). В колонках только культуры с РОВНО ОДНИМ типом тары.
  Заголовок колонки: чип цвета + название + приглушённо тип тары.
- **Вес рейса** — матрица фермер × культура, ячейка = плановый вес одной
  машины (т). Все культуры (тип тары не важен).
- **Тара: многотиповые** — для культур с ≥2 типами тары: селектор культуры
  → таблица фермер × разрешённые типы, ячейка = нетто-норма (кг).
  В шапке колонки типа — справочный брутто; предупреждение (янтарная рамка)
  при нетто ≥ брутто (не блокирует). Прототип: `docs/prototypes/norms-*.html`.
Во всех режимах: пустая ячейка = нет записи (≠0), автосейв по blur,
sticky шапка/первый столбец, tabular-nums.

## 6. Справочник культур (правка после B2.5)
В форме культуры: multi-select разрешённых типов тары + отметка одного
дефолтного (radio внутри выбранных). Ноль типов = навал (допустимо).
Server-валидация: ровно один is_default при ≥1 выбранном.

## 7. Приёмка (`/acceptance`)
Три зоны по BR-26 («Ожидают перевески» / «На приёмке» / «Принято»),
структура экрана и счётчики зон — из ВИДИМОГО набора (`filterBoard`).

### Тулбар
- Поиск. Оси: водитель · ТК · поставщик · культура · № акта.
  Кода машины в поиске НЕТ — он внутренний идентификатор БД и на
  экране не показывается (см. раздел 7 «Вне скоупа»).
- Фильтры: Поставщик, Сырьё (общий `FilterCombo`, как на ленте).
- Переключатель вида: **Список | По неделям**, состояние в URL
  `?view=` (дефолт — сплошной список), как `?week=`/`?view=` на ленте.
- Печать и Экспорт Excel — по текущему фильтру, всегда плоским списком.

### Вид «По неделям»
Группировка ВНУТРИ каждой зоны (зоны не смешиваются), ось — **дата
прибытия** машины, недели ISO. Шапка недели по образцу ленты: чип
`W{N}` (mono) + «Неделя N · даты года» + чипы культур + справа «N машин».
Тонн в шапке нет: в зонах 1/2 вес плановый/фактический, в зоне 3 —
принятый, единая цифра врала бы. Прошлые недели свёрнуты, текущая и
будущие развёрнуты; сворачивание независимо по зонам. Машины без даты
прибытия — отдельной корзиной «Без даты прибытия» в конце зоны.
Мобильная приёмка переключателя вида не имеет.

### Акт приёмки
Строка контракта принятых категорий по умолчанию наследуется от
`ShipmentItem.contract_line_id` (BR-10) — и в calibre-форме, и в
simple-поле. Нестандарт (`is_accepted=false`) дефолт НЕ получает
(двойной счёт с BR-33). Сохранённый акт при переоткрытии показывает
свои привязки, включая явное «— не в зачёт», — дефолт их не перетирает.

### Порядок категорий калибра (везде, где они показываются)
Категории идут **размерным** порядком — `6–9 см · 9–12 см · >12 см · Брак`,
одинаково в диалоге акта (десктоп и мобильный), чипах принятых машин,
стеке «Калибр», колонке «% категорий», справочнике культур и на печатном
листе. Правило и его обоснование — DOMAIN §5; реализация одна на всё
приложение (`compareCalibreRanges`). Раньше аналитика сортировала по доле,
и порядок колонок менялся от фермера к фермеру — сравнивать глазами было
нельзя. Форма культуры — исключение: там строки идут в порядке ввода
(пересортировка во время набора мешала бы), но после сохранения список
показывается размерным порядком.

### Профиль культуры — график «Динамика приёмки по неделям»
Три серии: **по перевеске (факт)** — область цветом культуры с
прозрачностью (`strokeOpacity .5`, `fillOpacity .05`), рисуется ПОД
приёмкой; **приёмка** — область тем же цветом в полную силу;
**плановый темп** — серый пунктир (`WeeklyPlan`, только при наличии плана).
Видимая полоса между факт-кривой и приёмкой = брак + нестандарт: ради
неё серия и добавлена. Новых цветов не вводится — база веса читается по
насыщенности одного и того же `Culture.color`.

### Профиль культуры — печатный лист
`/print/analytics/culture/[id]?season=` — A4 portrait, кнопка «Печать» в
шапке экрана (тот же паттерн `<a target="_blank" class="btn btn-sm">`, что
на дашборде). Состав: KPI-полоса · динамика и % брака по неделям · таблица
по поставщикам · стек калибра. Данные — тот же `getCultureAnalytics`, что
у экрана, поэтому числа совпадают тождественно; drill-down ссылок на листе
нет. Графики на печати ниже экранных (150px против 200px) — иначе лист не
помещается в страницу. Подвал без «лист 1/1»: число поставщиков переменное,
и лист законно может уйти на вторую страницу (как «Отгрузки»).

### Профиль культуры — таблица «По поставщикам»
Колонки: Фермер · Заявлено, т · Принято, т · К оплате, т · Выполнение ·
% категорий · Доля в культуре, плюс строка «Итого по культуре».
«% категорий» — мини-стек 100% фактического веса (миниатюра `an-calbar`:
оттенки культуры на принятых категориях, штриховка янтарём на «не в зачёт»
и браке) с mono-легендой под ним; брак от 6% выделен тоном. Отдельной
колонки «Брак» нет — она свёрнута сюда. Для simple-культур стек
вырождается в «Принято» + «Брак».

**Имена CSS-классов не должны совпадать с фильтрами блокировщиков
рекламы.** Класс `sharebar` попадал под generic-фильтр `##.sharebar`
(социальные списки EasyList/Fanboy) — uBlock Origin и AdGuard прятали
ячейку `display:none` на реальном домене, из-за чего на деплоях колонка
«Доля в культуре» была пустой, а на `localhost` работала. Сейчас
`an-share`/`scol`. Слова-приманки: `share`, `sharebar`, `social`,
`banner`, `ad`/`ads`, `sponsor`, `promo`, `popup`, `widget`.

### Карточка поставщика — вкладка «Расчёты»
Свод по строкам контракта, строка раскрывается в партии (chevron слева,
`-rotate-90` в свёрнутом виде; кликабельна вся строка). Раскрывающаяся
строка внутри `<Table>` — первый такой случай в проекте: `<TableRow>` +
`<TableCell colSpan>` с вложенным списком на `bg-muted/30`.

**Названия колонок разводят две базы веса** (DOMAIN §1): «Зачтено» — вес
в объём строки контракта, «К оплате» — оплачиваемый (зачтено + доплата
BR-33). Одно число двумя словами не называть: «Зачтено» строки и
«принято по акту» партии расходятся, когда нестандарт оплачивается своей
строкой (C3d-2), и это не ошибка. Поэтому у партии есть подстрока-разбор
`факт → принято по акту (N %) · нестандарт · брак`, а в подвале — сноска
«„Зачтено“ — то же число, что „Принято“ на вкладке Контракты».

**Два скоупа подписаны в шапке колонок:** периодные получают суффикс
(«за август»), сезонные — «за сезон». Строки без движения в периоде не
прячем: иначе исчезает «Заявлено» по недовыполненным строкам — самое
интересное в разговоре с фермером; рисуем приглушённо с нулями.

Колонка «Доплата» появляется только когда доплата в периоде есть
(конвенция проекта: нулевая доплата BR-33 явно не показывается). Чип
партии — `корректировка N %` (mono, uppercase, как в приёмке); зелёный
акцент `#1d8e75` всегда на числе, по которому платят («к оплате»).

Переключатель периода — `Button` + нативный `input[type=date]`
(shadcn calendar/toggle-group в проекте нет), состояние в URL, без
localStorage.

## 8. Вне скоупа (решено НЕ делать)
Индикаторы качества, PDF, «догруз по пути», код машины в UI,
чекбоксы актов, шапка колонок позиций, карандаши на строках позиций.

## 9. Отложено
Мобильная версия ленты — отдельный дизайн-промпт после стабилизации
десктопа в коде (после B3). Виды Heatmap и План — этапы B4/B5.
**Обновление (F/V2):** мобильная версия РЕАЛИЗОВАНА (responsive). **v1** — лента (просмотр), приёмка, контакты
водителей; шелл с нижним таб-баром + drawer, карточные списки (`mobile-v1.html`). **v2** — read-only Сводка
(сегмент на Ленте) и План (drawer «Планировщик»), карточки из `getPlanWeek` (`mobile-v2.html`).
