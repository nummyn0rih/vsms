## Что закрываем

**П-14 — нет индексов под реальные паттерны запросов.** Postgres не индексирует FK автоматически.
Проверено по схеме: у `StockMovement` есть `[kind, packaging_type_id]`, `[kind, ingredient_id]`,
`[from_location_id]`, `[to_location_id]`, но **нет** индекса по документу-источнику. Отсутствуют:

| Таблица | Индекс | Кто читает |
|---|---|---|
| `Shipment` | `[arrival_date]` | лента, доска, приёмка — все выборки фильтруют по дате прибытия |
| `StockMovement` | `[source_doc_type, source_doc_id]` | ВСЕ откаты и нетто-гарды плеч |
| `ShipmentItem` | `[shipment_id]` | загрузка позиций машины |
| `ChangeLog` | `[entity, entity_id]` | история правок |

**П-8 — гонка генерации кода машины.** `getNextCode` = `SELECT COALESCE(MAX(code::int),0)+1` внутри транзакции,
а `@unique` на `code` нет — БД дубль не остановит. **Сверх аудита:** ровно та же схема у
`getNextMaterialCode` для `MaterialShipment` (нумерация отдельная, но механика и дыра идентичны).

## Решения (зафиксированы)

| Развилка | Выбор |
|---|---|
| `MAX+1` vs Postgres sequence | **Оставляем `MAX+1` + `@unique` + retry на `P2002`.** Sequence корректнее при конкуренции, но даёт ДЫРЫ в нумерации (не откатывается), а `code` — рабочий номер машины, который люди называют вслух. Текущее поведение (номер переиспользуется после удаления плановой машины, BR-19) сохраняем |
| Где retry | **Вокруг всей `$transaction`**, не внутри: упавшую транзакцию нельзя продолжить. Побочных эффектов вне БД нет → повтор безопасен |
| Число попыток | 3, затем — человеческая ошибка пользователю |
| `CREATE INDEX CONCURRENTLY` | **Не используем.** Нужен DDL вне транзакции (Prisma так не умеет из коробки), а таблицы сейчас маленькие — блокировка на доли секунды. Пересмотреть, если данные вырастут на порядки |
| Обе сущности | `Shipment` и `MaterialShipment` — в одной миграции |

## ⚠ ПРЕД-ПРОВЕРКА НА ПРОДЕ — до всего остального [Ivan]

Уникальный индекс **не создастся, если в данных уже есть дубли**, и миграция упадёт на билде Vercel.
Проверить прод (psql из того же PG18-набора):

```bash
source ~/.config/neon/env   # PGURL_PROD / PGURL_DEV

/usr/local/opt/postgresql@18/bin/psql "$PGURL_PROD" -c \
'SELECT code, COUNT(*) FROM "Shipment" GROUP BY code HAVING COUNT(*) > 1;'

/usr/local/opt/postgresql@18/bin/psql "$PGURL_PROD" -c \
'SELECT code, COUNT(*) FROM "MaterialShipment" GROUP BY code HAVING COUNT(*) > 1;'
```
_(Intel-мак: Homebrew в `/usr/local`. Проверка выполнена — дублей нет.)_

Обе выборки должны вернуть **0 строк**. Если дубли есть — СТОП, не мигрировать: сначала решаем, какой машине
сменить номер (это правка реальных рабочих данных, а не техническая мелочь).

## Применение на прод

1. **Пред-проверка на дубли** (выше) — 0 строк в обеих выборках.

5. Прод-смоук: лента и приёмка открываются, номера новых машин продолжают прежнюю нумерацию.
