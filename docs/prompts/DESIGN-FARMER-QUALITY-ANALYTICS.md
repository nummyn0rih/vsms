# DESIGN-спека — вкладки «Качество» и «Аналитика» на карточке фермера (для Claude Design)

> Задача Claude Design: HTML-прототип **двух последних вкладок карточки поставщика** — «Качество» и
> «Аналитика». Дальше PM + пользователь ревьюят, правят, утверждают. Итог —
> `docs/prototypes/farmer-quality-analytics-v1.html`.
> Закрывает v2 «Экрана 4» PRD; в UI вкладки уже застолблены как `disabled` «скоро» (`FarmerCardTabs.tsx`).

## Контекст

Разрез **«фермеры внутри культуры»** реализован — `/analytics/culture/[id]`, таблица «По поставщикам».
Зеркального разреза **«культуры внутри фермера»** нет: перед разговором с поставщиком данные собираются
руками. Это и есть смысл обеих вкладок.

На карточке уже пять вкладок: Основное · Контракты · Расчёты · Отгрузки · Тара/ингредиенты. Выполнение
контракта, деньги, список партий и остатки там ЕСТЬ. Новые вкладки не должны их повторять — только то,
чего нет нигде: **сравнение с другими поставщиками** и **прогноз/темп**.

## Сценарии (все четыре подтверждены пользователем, разной частоты)

| Сценарий | Частота | Вкладка |
|---|---|---|
| Разговор с фермером о качестве | по факту проблем | **Качество** |
| Решение на следующий сезон (кому дать объём) | раз в год | **Качество** (итог сезона) |
| Оперативный контроль в сезон | еженедельно | **Аналитика** (период) |
| Прогноз поставок («сколько ещё машин ждать») | еженедельно | **Аналитика** |

Отсюда — граница: **«Качество» отвечает «какой он поставщик», «Аналитика» — «что с ним происходит сейчас
и чего ждать».** «Качество» сезонное, без переключателя периода (качество за неделю — это одна-две партии,
шум). «Аналитика» с периодом.

## Вкладка «Качество» (сезон целиком)

1. **Строка-шапка:** имя фермера · сезон · «сформировано ДД.ММ.ГГГГ» (моно, справа) — как на «Расчётах».
2. **KPI-полоса (4 плитки):** Принято, т · Средний брак, % (взвешенный по факт. весу) · Не в зачёт, %
   (Σ непринятых категорий — для calibre) · Партий с актом, шт.
3. **Ядро вкладки — таблица «По культурам»** (нового в системе нет ничего похожего):

   `Культура · Принято, т · Брак у него, % · Брак по культуре у ОСТАЛЬНЫХ, % · Δ · Позиция · Доля в культуре, % · Категории`

   - **Δ** — разница со средним по остальным поставщикам культуры; знак важнее величины (хуже/лучше).
   - **Позиция** — «N из M по этой культуре», **показывать только при M ≥ 3**: «2 из 2» — не рейтинг, а шум.
     При M < 3 — прочерк с подсказкой «мало поставщиков для сравнения».
   - **Категории** — мини-стек долей калибра (для simple-культур — «Принято / Брак»), размерный порядок.
   - Сортировка — по принятому объёму (важное сверху), как в таблице поставщиков культуры.
4. **Раскрытие строки культуры → партии** (переговорный лист): дата · № акта · факт, кг · принято, кг ·
   принято, % · брак, % · категории строкой. Это то, что зачитывают фермеру.
5. **Динамика брака по неделям** — показывать, **только если недель с актами ≥ 4**; иначе вместо графика
   таблица недель с подписью «для графика мало точек». У одного фермера за сезон 10–40 партий: линия по
   трём точкам врёт больше, чем говорит.
6. **Подпись внизу:** категории калибра берутся из действующей схемы, а не из снимка акта — правка схемы
   меняет качество прошлых партий. Лист уходит наружу, уточнить будет не у кого.

## Вкладка «Аналитика» (с периодом)

1. **Переключатель периода** — тот же, что на «Расчётах»: сезон (дефолт) · месяц · неделя · свой диапазон,
   состояние в URL. Компонент и логика уже есть (`SettlementPeriodBar`, `settlement-period.ts`).
2. **KPI-полоса (4–5 плиток):** Принято за период, т · Темп, т/неделя · Выполнение по контрактам, % (сезон) ·
   **Осталось ~N машин** · Ср. вес рейса: план / факт.
3. **«Осталось ~N машин» — по культурам** (в системе не реализовано нигде, PRD Группа 1):
   `(объём строки − принято) / средний вес рейса`. Разрез по культурам, итог сверху.
   - у культуры **без строки контракта** — «—», не 0 (правило уже принято на аналитике культуры);
   - подписать базу: считается по ФАКТИЧЕСКОМУ среднему весу рейса, а он занижается частично
     перевешенными машинами → оценка консервативная (известный компромисс, DOMAIN §5).
4. **Динамика приёмки по неделям** — принято/факт по неделям, серии цветом культуры; при недостатке точек —
   та же деградация в таблицу, что и на «Качестве».
5. **Ритм поставок:** последняя поставка N дней назад · типичный интервал между машинами · машин за период.
   Отвечает на «он вообще возит или пропал».
6. **Доля фермера:** в культуре и в сезоне (%).

## Состояния (показать все)

- **Фермер с полными данными, calibre-культура** — основной вид обеих вкладок.
- **Фермер только с simple-культурами** — блок категорий вырождается в «принято/брак», «Не в зачёт» скрыт.
- **Единственный поставщик культуры** (M < 3) — колонки сравнения и позиции с прочерком и объяснением.
- **Начало сезона:** актов нет, но контракты есть — KPI с «—», «Осталось ~N машин» считается от нуля
  принятого, тексты объясняют, а не показывают нули.
- **Фермер без контрактов** — «Аналитика» почти пуста; лист должен объяснять это, а не выглядеть сломанным.
- **Период без поставок** на «Аналитике» — как на «Расчётах»: явная строка вместо нулей.

## Визуальный язык (строго)

- Токены и паттерны — `DESIGN-SYSTEM.md` + существующие панели карточки фермера (`farmer-card-v1.html`) и
  профиля культуры (`culture-analytics-v1.html`). KPI-плитки — те же, что уже на карточке.
- Цвет культуры — из `Culture.color`; брак — нейтральный янтарь; Δ хуже/лучше — БЕЗ алярм-красного:
  это разговорный инструмент, а не авария.
- Числа — `tabular-nums`; № акта и ISO-недели — Geist Mono.
- Таблица важнее графика: графики только там, где отвечают на вопрос и где хватает точек.
- ЗАПРЕЩЕНО: деньги-KPI на «Качестве» (BR-33 намеренно не искажает статистику качества — колонка
  «к оплате» рядом с «% брака» сотрёт эту границу); эмодзи-иконки; радуга серий; светофорная заливка строк.

## Границы (реализм — что реально посчитается)

- Всё считается на лету, ничего не хранится. Новых формул НЕ вводить, переиспользуются:
  `computeWeightedBrak` · `computeAcceptedKg` / `computeAcceptedPercent` · `categoryShares` +
  `compareCalibreRanges` · `getContractExecution` · `getFarmerCard` · `TripWeightNorm`.
- **Бенчмарк** берётся тем же ядром, что таблица поставщиков культуры (`culture-agg.ts`, `bySupplier`):
  разворачивается разрез, а не пишется вторая агрегация.
- **Сравнение сезонов год-к-году — вне среза** (нет истории, этап G).
- Деньги — на вкладке «Расчёты», выполнение — на «Контрактах», список партий — на «Отгрузках»: не дублировать.
- Печать/экспорт этих вкладок — вне среза (отдельной задачей, если понадобится).

# РЕВЬЮ ПРОТОТИПА v1 (PM) — решения

> Прототип: `docs/prototypes/farmer-quality-analytics-v1.html`. Все шесть состояний собраны, деградации
> (M < 3, < 4 недель, нет контрактов, пустой период, начало сезона) отработаны и объяснены текстом.
> Ниже — ответы на открытые вопросы и правки к v2 прототипа / код-спеке.

## Ответы на вопросы прототипа

| № | Вопрос | Решение | Причина |
|---|---|---|---|
| 1 | Блок «5 худших партий сезона» поперёк культур | **Нет в v1** | Разговор с фермером идёт ПО КУЛЬТУРЕ («у вас перец плохой»), а не «вот пять худших вообще». Подсветки внутри раскрытой культуры хватает, а третий список партий (после «Отгрузок» и раскрытия) — это ещё один экран того же. Вернуться, если в реальном разговоре не хватит |
| 2 | «Ритм поставок» — оставить? | **Оставить целиком** | Состояние C1 доказало ценность: «17 дней при типичном интервале 6 — пропал». Из «Динамики приёмки» это не читается: там недельные суммы, разрыв внутри и между неделями не виден |
| 3 | Период на «Качестве» | **Нет в v1**, решение не окончательное | При < 5 партиях в окне бенчмарк сравнивает шум с сезонным средним. Запрос «как он вёл себя в августе» частично закрыт раскрытием партий с датами. Если понадобится — добавляется тем же компонентом, но с порогом на показ Δ и позиции |
| 4 | «Не в зачёт» как KPI-плитка | **Убрать из KPI, перенести числом в строку культуры** | У смешанного фермера это Σ по одной calibre-культуре из четырёх — цифра честная, но читается как общая. В строке культуры она однозначна. KPI становится **тремя плитками всегда** (принято · средний брак · партий с актом) — только величины, осмысленные для фермера целиком |

## Правки к прототипу / код-спеке

1. **Итоговая строка таблицы: «Брак у остальных» — без числа.** Сейчас в A0 стоит `3,4%` — это композит по
   разным культурам с разными базами, а выглядит сопоставимым с браком фермера. Оставить только словесную
   оценку («≈ на уровне» / «хуже» / «лучше») и подпись, по скольким культурам она посчитана. В B1 это уже
   сделано верно («только Томаты») — распространить на общий случай.
2. **B2 «начало сезона»: «Брак у остальных» как ориентир — только если у остальных ЕСТЬ акты.** В начале
   сезона их обычно тоже нет; в этом случае прочерк и подпись «сравнивать пока не с кем», а не пустая
   колонка с числом из ниоткуда.
3. **KPI «Ср. вес рейса план/факт» на «Аналитике»:** «план» — это `TripWeightNorm` по паре фермер×культура,
   у фермера с четырьмя культурами единого плана нет. Показывать взвешенным по принятому объёму и подписать
   базу; при отсутствии норм хотя бы у одной культуры — прочерк в плановой половине, как в C1.

## Ограничение реализации (важно для код-спеки)

**Не звать `getCultureAnalytics` в цикле по культурам фермера.** Он рассчитан на ОДНУ культуру и делает
5+ выборок, включая `allItems` (все позиции сезона с актами, `server/analytics/culture.ts:281`). Четыре
культуры → ~20 запросов и четырёхкратная загрузка позиций сезона.

Нужен отдельный загрузчик `getFarmerQuality({ farmerId, season })`:
- ОДНА выборка `shipmentItem` по `culture_id IN (культуры фермера этого сезона)` с актами — она даёт и
  позиции фермера, и позиции остальных поставщиков этих культур (база бенчмарка);
- разделение «его / остальные» — в памяти, существующей `filterItemsBySuppliers`;
- агрегация — существующими `aggregateCultureItems` / `categoryShares` / `computeWeightedBrak`, БЕЗ новых формул;
- знаменатель «доли в сезоне» — та же единственная выборка позиций сезона, не вторая.
