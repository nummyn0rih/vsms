## Фаза 2 — Neon: прод + dev ветки [Ivan]

> ⚠ **ВАЖНО на Free-плане: прод и dev — РАЗНЫЕ ПРОЕКТЫ Neon, не ветки одного проекта.**
> Лимиты Free считаются **на проект** (100 CU-часов, 0.5 GB, 5 GB egress), и при исчерпании любого из них
> **compute проекта суспендится до следующего биллингового месяца**. Если dev-ветка живёт в одном проекте с продом,
> активная разработка/preview-деплои жгут общий бюджет и могут **уронить прод в разгар сезона**, а починить это
> можно только апгрейдом плана. Разные проекты = отдельные бюджеты (Free разрешает до 100 проектов).
> Схему это не усложняет: миграции синхронизируются через git, а не через ветвление Neon.

1. Проект **`vsms-prod`** — прод. Его default-ветка = прод-БД. Больше веток в нём не заводить.
2. Проект **`vsms-dev`** — разработка/preview. Данные одноразовые. При необходимости — ветки внутри него
   (лимит 10) под параллельные фичи.
3. Для КАЖДОГО проекта скопировать **две строки**: pooled (`...-pooler...`, → `DATABASE_URL`) и direct
   (без `-pooler`, → `DIRECT_URL`). Итого 4 строки: прод×2, dev×2.
4. Учесть свойства Free-плана (проверено на neon.com/pricing, 26.07.2026):

   | Лимит Free (на проект) | Значение | Что это значит для VSMS |
   |---|---|---|
   | Compute | 100 CU-часов/мес | При исчерпании — **compute суспендится до след. месяца**. Главный риск доступности. |
   | Storage | 0.5 GB | Для таблиц поставок (числа/текст) — с большим запасом. |
   | History window (PITR) | **6 часов** (лимит 1 GB) | Откатиться можно только на 6 ч назад → **нужен свой `pg_dump`** (§8). |
   | Снапшоты | 1 ручной, **scheduled — нет** | Автобэкапов на плане нет. |
   | Scale-to-zero | через 5 мин, отключить нельзя | Первый запрос после простоя — холодный старт (заметная задержка). Для внутреннего инструмента терпимо. |
   | Protected branches | нет | Защита прод-ветки средствами Neon недоступна. |

   Если сезон пойдёт активно (несколько пользователей весь день) — 100 CU-часов может не хватить; тогда
   апгрейд прод-проекта на Launch (pay-as-you-go, без месячного минимума). Dev при этом остаётся на Free.

## Фаза 4 — Vercel: проект и переменные [Ivan]

1. Vercel → Add New Project → импорт `github.com/nummyn0rih/vsms`. Framework — Next.js (автоопределит).
2. Settings → Git: **Production Branch = `main`**. Остальные ветки (`dev`, фичи) → **Preview** автоматически.
3. Settings → Environment Variables — задать по областям:

   | Переменная | Scope **Production** (проект `vsms-prod`) | Scope **Preview** (проект `vsms-dev`) |
   |---|---|---|
   | `DATABASE_URL` | прод pooled | dev pooled |
   | `DIRECT_URL` | прод direct | dev direct |
   | `AUTH_SECRET` | **свежий** (`openssl rand -base64 32`) | свой, другой |
   | `AUTH_URL` | **можно не задавать** (см. ниже) | **не задавать** |

   Значения у Production и Preview разные → это **отдельные записи с разным scope**, а не одна на два окружения.
   В Vercel один и тот же ключ можно завести дважды с разными scope.

   🚨 **При выборе Environments НИКОГДА не ставить «Production and Preview» на `DATABASE_URL`/`DIRECT_URL`.**
   Билд гонит `prisma migrate deploy` — общая на два окружения строка означала бы, что **каждый preview-деплой
   фичевой ветки применяет свои миграции к ПРОД-БД**. Для прод-значений выбирать ровно **`Production`**,
   для dev-значений — ровно **`Preview`**.

   - **`AUTH_URL` можно не задавать вообще:** `trustHost: true` уже стоит в `auth.config.ts`, Auth.js берёт host
     из заголовков (на Vercel это корректный домен). Плюс до первого деплоя домен ещё неизвестен — курица-яйцо.
     Задавать имеет смысл только когда повесишь **свой** домен и захочешь зафиксировать канонический адрес;
     тогда — ровно `https://<домен>` без слеша на конце, scope `Production`. Неверное значение ломает логин,
     отсутствующее — нет.

   - **Scope `Development`** — не заполнять: он для `vercel dev`/`vercel env pull`, а локально используется свой `.env`.
   - **`AUTH_SECRET` нужен и в Preview:** без него NextAuth падает на preview-деплоях. Значение — своё, не прод-овское.
   - **`AUTH_URL` в Preview не задавать:** у каждого preview свой URL; при `trustHost: true` Auth.js берёт host из
     заголовков. Задать прод-домен в Preview = сломать логин на preview.
   - **`SEED_ADMIN_LOGIN`/`SEED_ADMIN_PASSWORD` в Vercel НЕ нужны.** Сид запускается один раз с твоей машины
     (Фаза 5 п.2), билд его не вызывает. Не держать пароль admin в переменных хостинга.

   ⚠ Прод `AUTH_SECRET` — НЕ dev-шный. Прод-пароль admin — не как в dev.

## Фаза 5 — Первый прод-деплой + сид admin

1. **[Ivan]** Merge `dev` → `main` (или первый деплой из `main`). Vercel build прогонит
   `prisma generate && prisma migrate deploy && next build` → миграции создадут прод-схему на чистой Neon-ветке.
> ⚠ **Успешный деплой НЕ создаёт админа.** Билд применяет только миграции (схему); `prisma/seed.ts` он не вызывает.
> До ручного прогона сида таблица `User` пуста и логин на проде невозможен — это не баг Auth.js.
> Переменные `SEED_ADMIN_*`, заданные в Vercel, ничего не создают: в рантайме их никто не читает.

2. **[CC/Ivan]** Сид первого admin в прод — один раз, локально против прод-БД:

   ```bash
   DATABASE_URL='<прод-pooled>' SEED_ADMIN_LOGIN='<логин>' SEED_ADMIN_PASSWORD='<пароль>' npm run db:seed
   ```

   ⚠ **Именно `DATABASE_URL`, не `DIRECT_URL`:** `prisma/seed.ts` создаёт клиент из `process.env.DATABASE_URL`
   (строка 23) — `DIRECT_URL` он не читает, и с ним сид молча ушёл бы в БД из локального `.env` (dev), а прод-логин
   не заработал бы. Инлайн-префикс перебивает `.env`, т.к. `dotenv/config` не переопределяет уже заданные env.
   Прямой коннект здесь не нужен: сид — это DML (`upsert`), pooler его тянет.

   **Перед сидом убедиться, что бьём в прод** (иначе admin уедет в dev):
   ```bash
   DATABASE_URL='<прод-pooled>' npx tsx -e "import {PrismaPg} from '@prisma/adapter-pg';import {PrismaClient} from './lib/generated/prisma/client';const p=new PrismaClient({adapter:new PrismaPg({connectionString:process.env.DATABASE_URL})});p.user.count().then(n=>console.log('users в этой БД:',n)).finally(()=>p.\$disconnect())"
   ```
   На чистой прод-БД ожидаем `0`. Если больше — это НЕ та база, остановиться.

   После сида: проверить, что создан ровно 1 пользователь `role=admin` (сид идемпотентен — повторный запуск
   не плодит дублей, а сбрасывает пароль/роль).
3. **[Ivan]** Открыть прод-URL, залогиниться admin-логином/паролем.

## Фаза 8 — Бэкапы [Ivan]

**На Free-плане своя резервная копия обязательна:** PITR = 6 часов, scheduled-снапшотов нет, ручной снапшот один.
Потеря данных старше 6 часов не восстановима средствами Neon.

- **Свой `pg_dump`** прод-БД — не опция, а необходимость. Хранить вне Neon (локально/облако), несколько поколений.
  ```bash
  /opt/homebrew/opt/postgresql@18/bin/pg_dump "$PROD_URL" -Fc -f vsms-prod-$(date +%F).dump
  ```
  ⚠ **Версия клиента должна быть ≥ версии сервера.** Neon на PG **18.4**; системный `pg_dump` 16.x падает с
  `server version mismatch` (обратной совместимости в эту сторону нет; пулер ни при чём). Ставится
  `brew install postgresql@18`, зовётся полным путём (Intel-мак: `/usr/local/opt/...`). `pg_restore` —
  из того же каталога, формат `-Fc` тоже завязан на версию.
  ⚠ **Строку подключения передавать переменной** (`"$PROD_URL"`), не вставлять текстом в чаты/issue/логи —
  в ней пароль. Если засветилась — сменить пароль роли в Neon и обновить обе переменные в Vercel + передеплой.
  Восстановление: `pg_restore -d '<целевой-URL>' --clean --if-exists vsms-prod-<дата>.dump`.
- **Частота:** в сезон — ежедневно (данные вводятся каждый день, потеря дня = потеря рабочего дня);
  межсезонье — еженедельно. Можно поставить scheduled-задачу-напоминание (скажи — оформлю).
- **Первый дамп** — сразу после ввода стартовых справочников (точка отката до операций).
- **Проверять восстановление**, а не только создание дампа: раз в сезон развернуть дамп в dev-проект и убедиться,
  что приложение поднимается. Непроверенный бэкап — не бэкап.

## Риски / на что смотреть

- **Прод-миграции необратимы по данным.** `migrate deploy` применяет всё незавершённое; деструктивную миграцию
  (drop/rename колонки) на прод — только с бэкапом и ревью. Правило dev-вайпа к проду НЕ применять.
- **Сид смотрит на `DATABASE_URL`.** `prisma/seed.ts` игнорирует `DIRECT_URL` и `prisma.config.ts`. Запуск сида
  без инлайн-`DATABASE_URL` уйдёт в БД из локального `.env` (dev) молча, без ошибки. Всегда задавать инлайн и
  сверять `user.count()` до запуска (Фаза 5 п.2).
- **Pooled vs direct.** Рантайм — pooled (`DATABASE_URL`), миграции — direct (`DIRECT_URL`). Перепутать = либо
  DDL-локи ломаются, либо рантайм упирается в лимит соединений. Обе строки нужны в каждой Vercel-области.
- **AUTH_SECRET прод.** Смена секрета инвалидирует сессии — задать один раз, не менять без нужды.
- **Preview делит dev Neon-ветку.** Несколько параллельных фич-preview с разными миграциями → конфликт на dev-БД.
  Solo: держать одну активную линию dev; при нужде — отдельная Neon-ветка на фичу.
- **Секреты.** Прод-строки/пароли — только в env Vercel, никогда в git. `.env` gitignored (проверено).
